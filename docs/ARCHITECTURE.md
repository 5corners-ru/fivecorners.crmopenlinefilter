# Архитектура

## Источник данных: штатный бейдж CRM, не своя синхронизация

Bitrix24 сам ведёт признак «есть непрочитанное сообщение открытой линии» на каждом Лиде/Сделке — это тот же механизм, что рисует жёлтый лейбл «чат с клиентами: НЕПРОЧИТАННЫЙ» на карточках канбана.

- Таблица: `b_crm_item_badge` (ORM-класс `\Bitrix\Crm\Badge\Model\BadgeTable`, ядро модуля `crm`).
- Поля: `ENTITY_TYPE_ID` (владелец — `CCrmOwnerType::Lead`/`Deal`), `ENTITY_ID`, `TYPE`, `VALUE`.
- Наш признак: `TYPE = 'open_line_status'`, `VALUE = 'not_read_chat'` (константы `\Bitrix\Crm\Badge\Type\OpenLineStatus::CHAT_NOT_READ_VALUE`).
- Пишет/удаляет запись **ядро**, в реальном времени, методом `syncBadges()` в `bitrix/modules/crm/lib/activity/provider/openline.php` — при каждом изменении статуса прочитанности активности открытой линии, привязанной к CRM-сущности.

Модуль **не подписывается ни на одно событие im/imopenlines** и не запускает никаких агентов синхронизации — он только читает уже готовые данные из `b_crm_item_badge` в момент применения фильтра.

## Точка расширения: DI-сервис `crm.filter.factory`

Стандартный фильтр CRM (Лиды, Сделки, Смарт-процессы) строится через фабрику `\Bitrix\Crm\Filter\Factory`, которая регистрируется как singleton-сервис в `Bitrix\Main\DI\ServiceLocator` под ключом `crm.filter.factory` (см. `bitrix/modules/crm/lib/Service/Container.php::getFilterFactory()`).

Никакого событийного хука вида `OnCrmFilterFieldsPrepare` для добавления псевдо-полей в фильтр в ядре нет — единственный официальный способ расширить набор полей фильтра и логику применения фильтра — подменить весь сервис `crm.filter.factory` своей реализацией, унаследованной от `Factory`.

Наш `FiveCorners\CrmOpenlineFilter\FilterFactory extends \Bitrix\Crm\Filter\Factory` переопределяет два метода:

- **`getUserFieldDataProvider()`** — добавляет в список полей фильтра псевдо-UF-поле `FCO_COLF_CHAT_READ` (чекбокс, subtype `boolean`) для сущностей Lead и Deal.
- **`getDataProvider()`** — оборачивает `applyCounterFilter()` у `LeadDataProvider`/`DealDataProvider`: перед вызовом родительской логики транслирует значение псевдо-поля в реальное условие фильтра (`ID IN (...)` / `ID NOT IN (...)` по списку ID из `b_crm_item_badge`), затем удаляет псевдо-поле из массива фильтра (иначе оно уйдёт дальше по цепочке и там не опознается).

## `DI\ServiceLocator` не переживает между HTTP-запросами

Регистрация `addInstance('crm.filter.factory', ...)` — не постоянная запись в БД, а объект в памяти процесса PHP. На каждый новый HTTP-запрос ServiceLocator создаётся заново со штатным содержимым. Поэтому подмену нужно переустанавливать **на каждый хит**:

- `lib/EventHandler.php::onProlog()` регистрируется как обработчик `main::OnProlog` (в `install/index.php::InstallEvents()`, по канону — не в `include.php`, см. `bitrix-module-rules` Правило 11).
- На каждом прологе, если модуль `crm` загружен, хендлер один раз вызывает `ServiceLocator::getInstance()->addInstance('crm.filter.factory', new FilterFactory())`.

Это не обработчик бизнес-события в привычном смысле, а обязательная per-request инициализация — общий паттерн для DI-подмен в Bitrix D7.

## Единоличное владение DI-ключом

`crm.filter.factory` — синглтон на весь запрос. Если два модуля независимо переопределяют этот же ключ (например, наш модуль и `dbogdanoff.crmfilter` одновременно), выигрывает тот `OnProlog`-обработчик, что выполнился последним (порядок в `b_module_to_module` не гарантирован явно). Оба фильтра одновременно работать не могут — см. README, раздел «Важно».

## Почему у модуля нет своих таблиц, UF-полей и admin-страниц

Псевдо-поле фильтра существует только в рамках HTTP-запроса, отрисовывающего/обрабатывающего фильтр — оно не сохраняется как реальное UF-поле сущности и не должно попадать в CRM-карточку. Настраивать модулю нечего: список сущностей (Лиды, Сделки) и текст поля зашиты в `FilterFactory`, потому что это именно то и только то, что было нужно на момент разработки (см. README «Зачем»). Расширение на другие CRM-сущности (Контакты, Компании, Смарт-процессы) потребует добавить аналогичные ветки `instanceof` в `getDataProvider()`/`getUserFieldDataProvider()`.
